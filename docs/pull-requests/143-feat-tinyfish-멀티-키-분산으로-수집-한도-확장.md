## PR Body

## 📌 개요

TinyFish 수집을 단일 키·분당 135개 로컬 제한에서 **여러 키를 활용하는 라운드 로빈 방식**으로 변경합니다. 요청을 키에 고르게 분산하고, 실제 HTTP 429를 받은 키만 잠시 제외해 다른 키로 수집을 이어갑니다.

## 🔍 배경: 기존 처리량의 한계

기존에는 `TINY_FISH_API_KEY` 하나를 사용하며, 프로세스 내부 카운터가 60초 동안 135개를 세면 다음 수집 요청을 차단했습니다. 미리보기·저장 후 분석·주기적 재수집이 같은 한도를 공유하므로, 요청이 몰리면 미리보기는 실패하고 분석은 SQS 재시도로 넘어갔습니다.

[TinyFish 공식 한도](https://docs.tinyfish.ai/fetch-api/reference#rate-limits)는 기본 **키별 150 URL/분**입니다. 이번 변경으로 로컬 카운터를 제거하고, 키 추가를 통해 사용 가능한 URL 예산을 늘릴 수 있게 합니다.

| 항목 | 기존 | 변경 후 |
| --- | --- | --- |
| 키 등록 | 단일 키 | 여러 키, 기존 단일 키 호환 |
| 호출 분산 | 같은 키로 모든 요청 전송 | 사용 가능한 키를 라운드 로빈으로 선택 |
| 한도 처리 | 135개에서 로컬 차단 | 실제 429를 받은 키만 cooldown |
| 다른 키 사용 | 불가능 | 429 발생 시 같은 URL을 다음 키로 재시도 |
| 모든 키 사용 불가 | 재시도 가능한 오류 | 기존 오류·SQS 재시도 정책 유지 |

## ✅ 작동 방식

### 1. 요청마다 다음 키를 선택합니다

```text
요청 A → 키 1
요청 B → 키 2
요청 C → 키 3
요청 D → 키 4
요청 E → 키 1
```

키 선택과 다음 순번 갱신만 동기적으로 수행합니다. **API 호출은 비동기이며, 앞선 요청의 응답을 기다리지 않고 다음 요청을 시작할 수 있습니다.** 같은 키에도 여러 요청이 동시에 진행될 수 있습니다.

### 2. 응답에 따라 다음 동작을 결정합니다

| 상황 | 처리 |
| --- | --- |
| 성공 | 수집 결과 반환 |
| TinyFish HTTP 429 | 해당 키를 cooldown에 넣고 같은 URL·옵션으로 다음 키 시도 |
| cooldown 중인 키 | 선택 시 건너뜀. 만료 후 다시 사용 가능 |
| 모든 키가 사용 불가능 | 기존 오류 반환. 미리보기는 실패 응답, 분석은 기존 SQS 재시도 |
| HTTP 401 | 인증 오류로 실패. 자동 전환·제외 없이 운영자가 설정을 확인하도록 로그 기록 |
| 그 외 오류 | 기존 오류 분류와 재시도 정책 유지 |

cooldown은 **`Retry-After`의 초 단위 값을 우선** 사용합니다. **단일 키로 200회 호출한 실험에서는 429 응답 50개 모두 `Retry-After: 60`을 반환했고, 마지막 429 약 61초 뒤 같은 키로 정상 수집이 재개됐습니다.** 이는 이번 실측 결과이며, 코드에서는 60초로 고정하지 않고 매 응답의 헤더 값을 따릅니다.

헤더가 없거나 잘못된 경우에는 서버에서 정한 fallback 값인 60초를 사용합니다. [공식 429 처리 지침](https://docs.tinyfish.ai/error-codes#rate_limit_exceeded)

한 URL에서는 각 키를 최대 한 번 시도하며, 키 전환을 포함한 전체 timeout은 25초입니다. 요청당 URL 하나를 유지하고 별도 배치·대기 큐는 추가하지 않습니다.

## 📈 키 개수와 호출 한도의 관계

TinyFish의 분당 한도는 API 키별로 적용됩니다. 이번 변경으로 등록된 여러 키에 요청을 분산해 **각 키의 할당량을 함께 활용**할 수 있습니다.

각 키의 한도가 150 URL/분이라면, 서로 다른 유효한 키 N개의 합산 한도는 **150 × N URL/분**입니다. 예를 들어 키 4개를 사용하면 합산 600 URL/분의 호출 예산을 구성할 수 있습니다.

## 🧪 검증 결과

### 실제 API 호출

공개 테스트 페이지 `https://example.com/`을 대상으로 확인했습니다.

| 실험 | 방법 | 결과 |
| --- | --- | --- |
| 멀티 키 분산 | 실제 공통 클라이언트로 키 4개, 순차 5회·동시 4회 호출 | **9회 모두 HTTP 200**, 정상 제목·본문 확인 |
| 선택 순서 | 순차·동시 호출의 키 선택 기록 | `1 → 2 → 3 → 4 → 1 → 2 → 3 → 4 → 1` 일치 |
| 실제 한도 | 별도 스크립트로 키 1개, 요청당 URL 1개, 최대 동시 10개로 200회 호출 | 약 10.2초 동안 **150회 성공·50회 HTTP 429** |
| 429 헤더 | 위 실험의 429 응답 50개 확인 | 모두 `Retry-After: 60`, `X-RateLimit-Limit: 150` |
| 키 복구 | 마지막 429 약 61초 뒤 같은 키로 추가 1회 호출 | HTTP 200, 정상 제목·본문 확인 |

실제 호출은 서버 전체 기동 없이 독립 실행했으며, 요청의 `ttl`은 기존 클라이언트와 같은 3600입니다. 실험 스크립트·결과는 임시 디렉터리에 두었고 실제 키와 함께 커밋에서 제외했습니다.

## 💬 리뷰어에게

현재 API 컨테이너 하나·Node 프로세스 하나 구성에 맞춰 키 상태를 Nest singleton의 메모리에 유지합니다. 프로세스를 여러 개로 늘리면 순번과 cooldown은 공유되지 않습니다.

401은 키 설정 오류를 명확히 드러내도록 기존 실패 정책을 유지합니다. 모든 키가 cooldown일 때도 기존 SQS 재시도 간격·횟수를 그대로 사용합니다.
