# 링크 검색 점수 산정

`GET /links?q=...` 검색 결과의 `score` 계산과 정렬 방법.
벡터 컬럼·코사인 계산 구조는 [벡터 검색 구조](./link-vector-search.md)에 있다.

관련 코드

| 파일                                | 역할                                        |
| ----------------------------------- | ------------------------------------------- |
| `link/search/search.service.ts`     | 후보 수집 조율, 커서 해석, 폴백             |
| `link/search/search.util.ts`        | 점수 계산·정렬·커서 슬라이싱 (DB 비의존)    |
| `link/link.repository.ts`           | 벡터 후보(`findVectorCandidates`)·키워드 후보(`findKeywordCandidateIds`) 쿼리 |
| `link/link.constants.ts`            | `LINK_SEARCH_*` 상수 (repository도 쓰므로 link/에 둔다) |

<br>

## 점수 = 코사인 유사도 + 키워드 가산점

```
score = 코사인유사도 + (검색어 포함 시 가산점)
      = [1 − (링크 임베딩 <=> 쿼리 임베딩)]  +  (키워드 일치면 +0.3, 아니면 0)
```

- **코사인 유사도**: 쿼리와 링크를 같은 임베딩 모델로 벡터화해 비교한다. **1에 가까울수록 유사**.
- **키워드 가산점**(`LINK_SEARCH_KEYWORD_BOOST = 0.3`): 검색어가 제목·도메인·URL·요약·메모에 **포함**되면 유사도에 더한다. 의미가 비슷한 것들 사이에서 검색어를 정확히 담은 링크를 위로 끌어올리는 용도다. 최종 점수는 **1로 클램프**한다.

<br>

## 순서 정하는 법

1. **벡터 후보**: 코사인 유사도 높은 순 상위 50개(`LINK_SEARCH_CANDIDATE_LIMIT`).
2. **키워드 후보**: `q`가 제목·도메인·URL·요약·메모에 부분일치하는 링크 최대 50개.
3. 두 후보를 합집합으로 모아 각 링크의 `score`를 계산하고 **`(score DESC, id DESC)`로 정렬**한다.
4. 커서 이후 구간에서 `limit`개를 잘라 응답한다.

점수가 같을 때 `id`로 tiebreak하는 이유는 커서 페이지네이션이다. 정렬이 흔들리면 페이지 경계에서 같은 링크가 중복되거나 빠진다.

<br>

## score 값

- **벡터+키워드 둘 다**: 유사도 + 0.3 (최대 1). 검색어를 정확히 포함한 의미 유사 링크 → 최상위.
- **벡터만**: 코사인 유사도 그대로.
- **키워드만(임베딩 없음)**: 유사도를 0으로 보고 가산점만 → 0.3.
- **일반 목록(검색 아님)**: `null`.
- 응답에는 **소수점 5자리로 반올림**해 내려준다(`LINK_SEARCH_SCORE_PRECISION`).

<br>

## 커서 페이지네이션

검색 결과는 점수 순이라 커서도 `(score, id)`를 담는다. 일반 목록의 커서는 `(정렬 컬럼 값, id)`라서 **두 커서는 서로 호환되지 않는다.** 검색 요청에 목록 커서를 넘기면 `400`(`INVALID_CURSOR`)이다.

```
nextCursor = base64url({ "v": "0.87342", "id": 42 })
```

`v`에 담는 점수는 응답 `score`와 **같은 반올림 값**이다. 쿼리 임베딩을 매 요청 재생성하면서 생기는 미세한 부동소수 차이가 페이지 경계를 어긋나게 하지 않도록 자릿수를 맞춰 비교한다.

후보 수집·정렬은 이미 메모리에 올라온 후보 풀(최대 100개) 안에서 이뤄지므로, 커서 적용은 `takeSearchPage`가 in-memory 필터로 처리한다. DB 왕복은 페이지당 후보 조회 2회 + 실제 행 조회 1회다.

`totalCount`는 **후보 풀 전체 크기**다. 커서와 무관하지만 `LINK_SEARCH_CANDIDATE_LIMIT` 때문에 최대 100으로 제한된다. 검색 결과를 100건 넘게 훑어야 하는 요구가 생기면 이 상수를 함께 올려야 한다.

<br>

## 임베딩 실패 시 폴백

쿼리 임베딩 호출이 실패하면(예: OpenAI 장애) 경고 로그를 남기고 **벡터 후보만 빈 배열로 두고** 키워드 후보로 계속 진행한다. 점수 공식·정렬 키·커서 형식이 그대로 유지되므로 페이지네이션이 중간에 끊기지 않는다. 이때 모든 결과는 키워드 가산점만 받아 `score = 0.3`이 되고, 순서는 `id DESC`(최신 저장순)가 된다.

<br>

## 튜닝 포인트

- 정확 일치를 더/덜 띄우려면 `LINK_SEARCH_KEYWORD_BOOST` 조정(현재 0.3).
- 후보 수와 `totalCount` 상한은 `LINK_SEARCH_CANDIDATE_LIMIT`(현재 50, 경로별).
- 키워드 매칭은 쿼리·컬럼 양쪽을 **공백 제거·소문자로 정규화한 뒤** `LIKE` 부분일치시킨다(`시드링크`=`시드 링크`, 대소문자 무관). 정규화 때문에 인덱스를 타지 못하지만 사용자 범위로 좁힌 스캔이라 감당 가능하다. 형태소 분석은 없어 조사·어간 변형은 못 잡는다.

<br>

## 아직 안 들어간 것 — 태그

키워드 매칭 대상(`buildKeywordCondition`)과 임베딩 대상 텍스트(`buildEmbeddingText`) 둘 다 **태그를 포함하지 않는다.** 태그 기능 자체가 아직 미구현(`LinkService.createTag`가 `NotImplementedException`)이라 붙일 대상이 없다.

태그 구현 시 검토할 두 갈래:

1. **임베딩 텍스트에 태그를 합친다** — 지금처럼 제목·요약·메모를 뭉쳐 한 벡터로 만드는 방식에 태그를 끼워 넣는다. 구현은 `buildEmbeddingText`에 한 줄 추가로 끝나지만, 태그가 바뀔 때마다 재임베딩이 필요하고 태그의 기여도를 따로 조절할 수 없다.
2. **태그 일치를 별도 점수 항목으로 둔다** — 키워드 가산점처럼 태그 일치에 독립 가중치를 준다. 태그는 사용자가 붙인 명시적 분류라 본문 부분일치보다 신뢰도가 높아 가중치를 다르게 줄 여지가 있다.
