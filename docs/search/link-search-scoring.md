# 링크 검색 점수 산정

`GET /links?q=...` 검색의 후보 수집, 점수, 정렬, 페이지네이션 규칙을 정리한다. 벡터 저장과 유사도 계산은 [벡터 검색 구조](./link-vector-search.md)를 참고한다.

## 구조

| 파일                                     | 역할                                            |
| ---------------------------------------- | ----------------------------------------------- |
| `link/search/search.service.ts`          | 신호별 후보 수집, hydrate, 최종 30개 상한, 커서 |
| `link/search/search.repository.ts`       | 제목·폴더·태그·본문·벡터 후보 쿼리              |
| `link/link-similarity.util.ts`           | 공용 토큰화·cosine 유사도 정규화                |
| `link/search/search-ranking.ts`          | 검색 신호 계산과 `(score DESC, id DESC)` 정렬   |
| `link/search/search-ranking.constant.ts` | 검색 기본 가중치                                |

## 후보 수집

검색어를 소문자화하고 Unicode 문자·숫자 토큰으로 나눈다. NFKC 호환 정규화는 적용하지 않으며, 키워드 후보 조회와 키워드 점수에는 앞의 최대 12개 토큰을 동일하게 사용한다. 다음 다섯 경로에서 각각 최대 30개를 회수한다.

1. 제목 부분일치
2. 폴더명 부분일치
3. 태그 `normalizedName` 부분일치
4. AI 요약·메모·도메인·URL·metadata description 부분일치
5. 전체 검색어의 쿼리 임베딩 코사인 유사도

쿼리 임베딩과 네 keyword 후보 조회는 동시에 시작한다. 임베딩이 먼저 완료되면 keyword 조회 완료를 기다리지 않고 바로 벡터 후보 조회를 시작한다.

키워드 경로는 대상 필드를 소문자화하고 공백만 제거한 표현식에 `LIKE '%token%'`을 적용한다. 점수 계산도 같은 대상 표현식을 사용하므로 구두점 경계를 후보 단계와 다르게 제거하지 않는다. `pg_trgm` GIN 표현식 인덱스는 제목, 본문, 태그에 각각 존재한다. 폴더명은 사용자별 폴더 수가 링크 수보다 작다는 전제로 활성 폴더 범위를 조회하며 별도 trigram 인덱스는 두지 않는다. 1~2자 검색어는 추출할 trigram이 없어 사용자 범위 스캔으로 퇴화할 수 있다.

후보 합집은 최대 150개이며, 이 후보 풀을 재랭킹한 상위 30개만 노출한다. 전체 사용자 범위의 exact top 30을 보장하는 구조는 아니다. API `limit`은 기본 9, 최대 30이며 이 30개 안에서 cursor 페이지네이션한다.

`folderId`, `unassigned`, `favorite`, `deleted`는 후보 범위에 적용한다. 검색 정렬은 관련도로 고정되므로 `sortBy`, `order`는 후보를 제한하지 않는다.

## 신호와 기본 가중치

각 신호를 0~1로 만든 뒤 가중 합산한다.

| 신호             | 원점수                                          | 기본 가중치 |
| ---------------- | ----------------------------------------------- | ----------: |
| `titleKeyword`   | 검색 토큰 중 제목에 부분일치하는 비율           |        0.10 |
| `folderKeyword`  | 검색 토큰 중 폴더명에 부분일치하는 비율         |        0.15 |
| `tagKeyword`     | 검색 토큰 중 개별 태그 하나에 부분일치하는 비율 |        0.10 |
| `contentKeyword` | 검색 토큰 중 본문 묶음에 부분일치하는 비율      |        0.05 |
| `embedding`      | `clamp(1 - cosineDistance, 0, 1)`               |        0.60 |

```text
score = titleKeyword * 0.10
      + folderKeyword * 0.15
      + tagKeyword * 0.10
      + contentKeyword * 0.05
      + embedding * 0.60
```

키워드 점수는 후보 검색과 동일하게 대상 필드의 소문자화·공백 제거 후 부분일치를 사용한다. 따라서 `머신러닝`과 `머신 러닝`, `nest`와 `nestjs`는 일치하지만 `designsystem`과 `design-system`처럼 구두점을 사이에 둔 문자열은 일치하지 않는다. 태그도 각 `normalizedName` 안에서만 비교하므로 서로 다른 태그의 경계를 이어 붙여 일치시키지 않는다.

전각·반각 같은 호환 문자는 lexical 단계에서 합치지 않는다. 저장 문자열과 같은 문자 체계로 검색하면 일치하지만 `NestJS`와 `ＮｅｓｔＪＳ`의 교차 표기는 lexical 일치로 보장하지 않으며, 의미 검색은 embedding 신호가 보완한다.

링크 임베딩이 아직 없어 `embedding=null`이면 이를 비유사도 `0`으로 간주하지 않는다. 해당 후보에서 embedding 가중치 `0.60`만 제외하고 lexical 가중치 합 `0.40`으로 점수를 재정규화한다.

```text
scoreWithoutEmbedding = (titleKeyword * 0.10
                       + folderKeyword * 0.15
                       + tagKeyword * 0.10
                       + contentKeyword * 0.05) / 0.40
```

실제로 계산된 embedding 원점수 `0`은 결측값이 아니므로 기존 가중치에 따라 비유사 신호로 반영한다. 관련 링크도 embedding을 계산할 수 없으면 같은 원칙으로 context 가중치 합 `0.45`를 사용한다.

## 정렬과 커서

모든 후보의 점수를 먼저 소수점 5자리로 반올림한 뒤 `(score DESC, id DESC)`로 다시 정렬하고 상위 30개를 선택한다. 응답 점수와 커서 비교 값이 같은 정밀도와 순서를 사용하므로, 반올림 후 동점이 된 후보도 id 순서대로 다음 페이지에 이어진다.

```text
nextCursor = base64url({ "v": "0.87342", "id": 42 })
```

`totalCount`는 커서와 무관한 상위 검색 결과 크기로 최대 30이다. 일반 목록 커서와 검색 커서는 서로 호환되지 않는다.

## 임베딩 실패 폴백

쿼리 임베딩 호출이 실패하면 경고 로그를 남기고 제목·폴더·태그·본문 신호로 검색을 계속한다. 이때 embedding은 결측 신호로 처리해 lexical 가중치 합 `0.40`으로 재정규화하며 커서 형식은 변하지 않는다.

검색 결과는 요청 시점마다 다시 계산하므로 페이지 사이에 embedding provider의 성공·실패 상태가 바뀌면 후보와 점수 순서도 달라질 수 있다. fallback 중 받은 cursor를 다른 ranking mode의 스냅샷으로 보장하지 않으며, 장애 전후에 페이지 결과가 불안정하면 첫 페이지부터 다시 조회해야 한다.

## 관련 링크와의 관계

검색과 관련 링크는 문자열·태그·cosine 유사도 계산만 `link-similarity.util.ts`에서 공유한다. 후보 쿼리는 `SearchRepository`와 `RelatedLinkRepository`, 점수 정책은 각각 `search/`, `related/` 내부에서 독립적으로 관리한다.

## 가중치 조정 근거

한 master 사용자의 활성 링크 181개를 대상으로 Search 121개와 Related 78개, 총 199개 평가 케이스에 1,279개 관련성 라벨을 구성했다. 개발·음식뿐 아니라 금융, 원예, 사진, 음악, 기후, 언어 학습, 육아, 스포츠, 건축, 반려동물 등 주제를 분산했고, Search에는 자연어 의도형 질의와 실제 제목에 가까운 질의를 함께 포함했다.

평가 케이스는 다음 기준으로 나눴다.

- `조정용 평가셋`: 여러 가중치 후보를 비교하고 최적 후보를 고르는 데 사용한다.
- `검증용 평가셋`: 가중치 선택에는 사용하지 않고, 선택한 가중치가 조정용 데이터에만 과도하게 맞춰지지 않았는지 확인한다.
- Related 재탐색은 기존형·제품형 사례가 한쪽으로 치우치지 않도록 두 집단을 같은 비중으로 평가하고, 개발 사례 57개를 5개 폴드로 교차 검증했다. 남은 review 21개는 최종 후보 확인에 사용했다.

관련성 판단의 주관성을 감안해 미판정 결과를 제외한 지표와 미판정을 무관으로 보는 보수적 지표를 함께 확인했으며, 최종 판단에는 다음 기준을 사용했다.

- `nDCG`: 관련성이 높은 링크가 상위에 배치되는지 확인한다.
- `Recall`: 관련 링크를 상위 결과 안에서 충분히 회수하는지 확인한다.
- `MRR`: 첫 번째 관련 링크가 얼마나 빨리 나타나는지 확인한다.
- 후보 커버리지와 실제 상위 결과를 함께 검토해 가중치만으로 해결할 수 없는 후보 생성 누락을 구분한다.

검증용 평가셋의 후보 커버리지는 Search 96.1%, Related 96.3%였다. 후보에 포함되지 않은 정답은 이후 정렬 가중치로 복구할 수 없으므로 이 수치는 랭킹 지표와 별도로 관리한다.

### Search

기존 평가 당시 가중치 순서는 `titleKeyword / tagKeyword / contentKeyword / embedding`이다. 폴더명 검색을 지원하면서 정확한 폴더명으로 검색한 8개 사례를 추가해 `titleKeyword / folderKeyword / tagKeyword / contentKeyword / embedding` 5개 신호의 3,701개 조합을 재탐색했다. 가중치 선택에는 기존형 tuning과 폴더형 tuning을 같은 비중으로 사용하고, 제목 가중치는 최소 0.10으로 제한했다. 폴더명 사례는 사용자 데이터가 외부 임베딩 API로 전송되지 않도록 lexical 신호만 사용했다.

| 후보             | 가중치                             | 기존형 holdout 보수적 nDCG | 기존형 Recall | 폴더형 holdout 보수적 nDCG | 폴더형 Recall |
| ---------------- | ---------------------------------- | -------------------------: | ------------: | -------------------------: | ------------: |
| 폴더 추가 초기값 | `0.10 / 0.10 / 0.25 / 0.10 / 0.45` |                      0.842 |         0.797 |                      0.764 |         0.892 |
| 균형 선택값      | `0.10 / 0.15 / 0.10 / 0.05 / 0.60` |                      0.843 |         0.783 |                      0.856 |         1.000 |

표는 미판정 결과도 실제 순위를 차지하는 것으로 계산한 보수적 지표다. 기존형 holdout은 폴더형 사례를 제외한 기존 검색 사례이고, 폴더형 holdout은 가중치 선택에 사용하지 않은 `유틸리티`, `디자인 꿀팁`, `자기계발`, `예쁜 카페` 폴더 사례다. 균형 선택값은 기존형 Recall이 0.014 낮아지는 대신 기존형 보수적 nDCG를 0.001 높이고, 폴더형 보수적 nDCG를 0.092, Recall을 0.108 높였다. 제목 검색의 기본 동작을 유지하기 위해 탐색 최적값이 더 낮더라도 제목 가중치는 0.10을 유지했다.

최소 점수 임계값 0.05는 조정용 지표를 개선하지 않았고 검증용 평가셋의 관련 결과 통과율만 96.1%에서 95.8%로 낮췄다. 0.075 이상에서는 Recall도 감소했으므로 임계값은 적용하지 않았다.

### Related

가중치 순서는 `folder / tag / title / embedding`이다. 단일 조정/검증 분할 결과에 의존하지 않도록 기존형 조정·제품형 조정·기존형 검증·제품형 검증의 네 하위집단을 구성했다. 829개 조합 중 가장 낮은 하위집단 nDCG를 우선 높이고, 이후 전체 평균 nDCG와 Recall을 비교하는 안정성 기준으로 다시 탐색했다.

| 후보               | 가중치                      | 개발 전체 보수적 nDCG | 개발 전체 Recall | review 보수적 nDCG | review Recall |
| ------------------ | --------------------------- | --------------------: | ---------------: | -----------------: | ------------: |
| 변경 전 main       | `0.20 / 0.30 / 0.15 / 0.35` |                 0.779 |            0.680 |              0.893 |         0.803 |
| 5-fold 최빈 후보   | `0.15 / 0.20 / 0.05 / 0.60` |                 0.801 |            0.692 |              0.906 |         0.832 |
| 안정성 기준 최종값 | `0.10 / 0.25 / 0.10 / 0.55` |                 0.796 |            0.697 |              0.904 |         0.822 |

5-fold 최빈 후보는 개발·review nDCG를 각각 0.005, 0.002 높였지만 개발 Recall을 0.005 낮췄다. 폴드별 선택값도 한 폴드에서는 tag 0.45까지 변했고, 각 폴드 밖 성능 평균은 보수적 nDCG 약 0.796, Recall 약 0.689로 최종값의 개발 전체 0.796, 0.697보다 낫지 않았다. 네 하위집단의 최저 성능을 우선한 재탐색에서는 `0.10 / 0.25 / 0.10 / 0.55`가 다시 선택됐으므로 이를 최종값으로 유지한다. 이는 기존 main 값으로 되돌린 결과가 아니라, 확장 평가셋의 하위집단 안정성을 기준으로 독립적으로 선택한 결과다.

이 결과는 한 사용자 데이터와 수동 관련성 판단에 기반한 오프라인 평가이므로 전체 사용자에 대한 보편적 최적값을 의미하지 않는다. 데이터 분포나 embedding 모델이 바뀌면 기존 검증용 평가셋만 반복해서 맞추지 말고 새 판정 데이터를 추가해 다시 검증해야 한다.

평가 데이터와 실행 도구는 아직 일회성 실험 수준이므로 저장소에 포함하지 않는다. 반복 운영이 필요해지면 평가 케이스·판정 이력·가중치 버전을 관리하는 내부 평가 기능으로 구현한다.
